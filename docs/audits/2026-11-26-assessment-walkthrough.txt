PRIORITY FINDINGS

1. HIGH: Incomplete baseline is labelled ready for a report.
Reproduction: after entering lifestyle/fitness and the first movement pattern, click Generate Report. Dialog showed Completion 50%, but also Ready to generate the report, with an enabled Generate Report action. No missing-test list appeared. Kept editing rather than generating a deliberately incomplete report.
Impact: coach can reasonably believe a partial baseline is complete and finish too early. Generate Report was visible from early lifestyle screens.
Code confirmation: src/lib/assessmentCompleteness.ts treats full mode as complete when ANY pillar score is above zero. usePhaseFormSubmitLabels.ts feeds that result to AssessmentReviewCheckpoint.tsx.
Recommended correction: baseline completion should follow required captured sections, separate draft saving from finalization, and identify remaining sections.

2. HIGH: Manual posture findings disappear from the client report.
Reproduction: manual observation recorded forward head and rounded shoulders; remaining posture selections neutral. Report completed but contained no Posture section or these findings, including after reopening.
Impact: coach spends time collecting findings with no visible client-facing result.
Code confirmation: buildPostureModel in src/lib/reports/buildClientReportModel.ts returns null when neither photos nor postureAiResults exist; manual posture fields are not included.
Recommended correction: carry manual observations into a plain-language report subsection without requiring photographs.

3. HIGH: Implausible strength input passes without warning.
Reproduction: entered 2525 pushups for the one-minute test, clicked Next and reached Grip. Back showed 2525 retained. Corrected to 18 before generating the saved report.
Impact: an extra digit can silently affect scoring and the debrief.
Recommended correction: numeric bounds and an explicit plausibility warning before section completion and final save; support legitimate zero scores.

4. MEDIUM: Report language contradicts the answers and entry guidance.
- Hydration answer: I try to stay hydrated but often forget. Report: Good / On track and You drink enough through the day.
- Nutrition answer: I try to eat healthy but struggle with consistency. Report: Good / On track, losing the stated inconsistency.
- Sleep table: Good / On track, while the lifestyle summary says sleep could be better.
- Resting HR 74: entry guidance for women 36-45 classed 67-74 as Good; report called resting HR a little high.
- Movement summary: Your joints move freely. Keep doing what you're doing, directly above two patterns needing work.
Code confirmation: assessment.ts maps the hydration/nutrition answers above to good. Client lifestyle factors display the stored category; clientPillarSummary.ts selects fixed strong/nudge copy using detail-score thresholds. The UI and narrative therefore use different signals.
Recommended correction: preserve answer meaning and align narrative, status labels, and input reference bands. This audit establishes internal inconsistency; it is not a clinical validation of the normative bands.

5. MEDIUM: Analyzer manual entry remains unnecessarily large.
Observed eleven analyzer fields including fat mass, five segmental lean values and BMR, despite the intended slim confirmation. Optional fields were not clearly distinguished. The section could be completed using muscle, BF%, WHR and visceral fat without those extra fields.
Impact: coach may search a printout for values that are unnecessary, or assume missing optional data blocks progress.
Recommended correction: emphasize weight/BF%/muscle, optional visceral/WHR, and keep height where needed; remove nonessential analyzer fields from this capture step.

6. MEDIUM: Movement completion behaves differently depending on the answer.
Looks good immediately saves and advances. Selecting a fault needs Section Complete. The immediate transition can make the coach's next pain/continue click land on the following pattern. Looks good is visually prominent even before a choice is made.
Code confirmation: MovementPatternCapture.tsx handleLooksGood calls onComplete immediately and applies benign values, preserving an existing explicit pain answer.
Recommended correction: use a consistent, clearly signposted completion action; ensure pain is deliberately recorded. Also reset scroll when changing patterns: during this run the next pattern opened with its title partially clipped above the viewport.

7. MEDIUM: A secondary save write failed silently.
Captured console warning at save: [Assessment] Failed to write consent record (non-fatal): FirebaseError: Missing or insufficient permissions.
Assessment/report save itself succeeded and survived reload.
Code location: src/hooks/useAssessmentSave.ts attempts organizations/{org}/clients/{client}/consents/health_data_v1 after the main save and catches the failure. Current firestore.rules does not contain a matching consents-specific rule.
Recommended correction: investigate the intended consent-record flow and narrow authorization for that write. Do not broaden client-data permissions as a workaround. No legal-compliance conclusion was made in this audit.
